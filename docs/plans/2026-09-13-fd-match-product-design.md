# FD 完整棋盘对局产品设计

> 文档状态：已确认设计基线  
> 日期：2026-09-13  
> 适用范围：`D:\fd` 的 7 人半自动/本地全人工测试、多人实时对局与 11 回合完整产品层  
> 规则来源：规则书、结构化主从 JSON、服务端 MatchSession 投影；本文不重新发明卡牌规则

## 1. 目标与边界

本设计把 FD 从“可以调用解释器的测试页面”整理为可实际完成一局游戏的桌面端棋盘产品。首要使用场景是：一名测试者在同一浏览器中依次操作 7 对主从；随后复用同一套界面与后端命令支持 7 个客户端实时对局。

产品必须做到：

- 完整推进 11 回合，并准确区分回合开始、准备、前哨、行动、战斗、清理和回合结束。
- 当前优先玩家由真人操作；本地测试模式可按席位自动切换真人视角，半自动模式可让其他席位使用确定性 AI。
- 所有合法操作、支付范围、目标候选、响应顺序和隐藏信息由后端投影决定。
- 玩家能看清棋盘、事件、占位、手牌、技能、攻击区、令咒、牌库摘要和弃牌堆，不依赖日志猜测状态。
- 无法自动结算的操作进入明确的玩家或房主裁定窗口，并暂停推进。
- 操作、状态变化、战斗 breakdown、裁定和恢复点都有结构化记录。

本文描述目标产品，不代表当前代码已经全部达到该状态。验收只能使用 `IMPLEMENTED_UNVERIFIED`、`COMPONENT_VERIFIED`、`SCENARIO_VERIFIED`、`E2E_VERIFIED` 等证据状态，不能仅凭页面存在或测试全绿宣称完成。

## 2. 核心设计原则

### 2.1 服务端权威

前端只呈现后端返回的选择，不自行推断规则：

```text
MatchSession 状态
  -> 玩家权限投影
  -> legalActions + interactionWindows + visibleZones
  -> 前端呈现
  -> 玩家选择 command
  -> 服务端重新校验并执行
  -> 新 revision 与结构化日志
```

禁止前端自行判断“这个地点应该能去”“这张牌应该能多打一张”“这个技能应该在此阶段显示”。前端可以做输入格式校验，但最终合法性始终由服务端确认。

### 2.2 焦点式交互

棋盘用于理解公共局势，操作台用于完成当前玩家的精细操作。两者不同时争夺同等空间：

- 观察状态：棋盘占主区域，操作台压缩为 104-136px 摘要栏。
- 操作状态：操作台展开至视口高度的 52%-60%，棋盘缩至上方并轻度降亮度。
- 支付、选目标和响应时保留必要棋盘上下文，不使用会让地点和候选失真的重度模糊。
- 完成或放弃当前操作后，操作台自动回到观察状态；玩家也可锁定展开。

### 2.3 一套交互支持本地与联网

本地七席全人工、单人加 AI、七客户端联网使用相同的 `dispatch` 路径。区别只在“谁决定当前 legal action”，不在规则执行方式。

### 2.4 信息按任务分层

- 第一层：当前阶段、优先玩家、必须处理的决定。
- 第二层：棋盘位置、事件、地利、参战者和公开攻击。
- 第三层：本人手牌、技能、支付资源和私有牌堆。
- 第四层：日志、完整区域、回放、房主工具。

日志不能代替第一到第三层的产品界面。

## 3. 信息架构与桌面布局

目标桌面宽度为 1280px 以上，优先适配 1440p 和 2560×1440。低于 1100px 时进入可滚动的紧凑桌面布局，不把完整棋盘强行压成手机页面。

```text
┌──────────────────────────────────────────────────────────────────────┐
│ 房间/连接状态 | 7 席位 | 回合·阶段·优先权 | 保存·恢复·重连·视角       │
├──────────────────────────────────────────────────────────────────────┤
│ 局势牌与阶段轨迹                                                     │
├───────────────────────────────────────────────┬──────────────────────┤
│                                               │ 当前决定             │
│                战 场 棋 盘                    │ 交互窗口             │
│  工房 / 深山町 / 新都 / 侦察                  │ 可选能力             │
│  地利槽 + 玩家头像 + 横排事件牌                │ directive / 错误      │
│                                               │ 日志 / 战斗详情       │
├───────────────────────────────────────────────┴──────────────────────┤
│ 本人作战中心：观察摘要（默认） / 52%-60vh 展开操作台                 │
└──────────────────────────────────────────────────────────────────────┘
```

### 3.1 顶部全局栏

顶部栏始终固定，包含：

- 房间号、连接状态、当前客户端身份。
- 七个席位按钮：席位号、玩家名、主从小头像、VP、魔力、令咒、淘汰状态。
- 当前回合、阶段、子步骤、优先玩家和等待对象。
- 保存、恢复、断线、重连、切换观战/本地席位。
- 房主工具入口，仅在权限允许时显示。

切换席位只改变可见投影，不能绕过服务端权限。联网对局中，普通玩家不能切换到别人的私有视角。

### 3.2 阶段轨迹

阶段轨迹显示七个稳定节点：

```text
回合开始 -> 准备阶段 -> 前哨阶段 -> 行动阶段 -> 战斗阶段 -> 清理阶段 -> 回合结束
```

当前节点高亮，已完成节点弱化，未来节点不可点击推进。阶段说明来自 MatchSession 的状态标签，不通过字符串包含关系猜测。

## 4. 回合与席位交互流程

### 4.1 回合开始与事件放置

1. 应用本回合局势牌及其持续规则。
2. 按回合和局势效果向战场放置事件牌。
3. 新都暗置事件保持背面；只有规则指定时才翻开。
4. 事件牌库不足时按规则回收事件弃牌并洗回，使用确定性随机源记录 seed。
5. 进入准备阶段并补牌至规定手牌数。

高潮阶段的基础调度为：前两个高潮回合深山町放两张明置事件，新都放一张明置和一张暗置事件；最终回合关闭新都，在深山町放三张事件。局势牌造成的额外放置叠加于基础调度，并由后端给出最终 placements。

### 4.2 准备阶段

准备阶段发生在事件放置和抽牌之后、前哨部署之前。当前席位只能看到：

- 后端提供的准备阶段能力。
- 令咒或替换牌库等明确允许在准备阶段使用的操作。
- “完成准备”操作。

没有准备阶段能力的玩家只能完成准备，不能看到部署按钮。起源弹等自行选择替换牌库的效果在此阶段打开卡牌选择窗口。

### 4.3 前哨阶段

每个尚未部署的玩家依席位顺序进行：

- 选择后端给出的合法部署地点和合法地利/工房槽位。
- 选择前哨阶段能力是否发动。
- 普通部署不能进入侦察；特殊许可必须由后端 legal action 明确给出。
- 部署至魔术工房后，按实际占据的工房槽立即获得对应魔力。
- Kayneth 等强制部署规则直接缩小合法候选，而不是只显示 directive 提醒。

完成当前席位后，本地七席模式自动切换到下一个待操作席位。所有席位完成后才进入行动阶段。

### 4.4 行动阶段

单个玩家的行动拆成可追踪子步骤：

```text
行动开始能力 -> 移动/不移动 -> 移动后能力 -> 选择并暂存攻击
-> 确认攻击 -> 追加/响应窗口 -> 完成行动
```

行动阶段的普通移动、令咒移动、急行移动和其他卡牌移动使用不同命令来源，但共享地点候选与占用校验。候选只能来自后端。

普通玩家默认每回合只能提交规则允许数量的攻击牌。额外打出、追加打出、援护射击等必须由明确的 modifier/interaction window 增加额度，不能因为前端允许拖入就绕过限制。

### 4.5 战斗、清理与回合结束

- 按战场分别确认参战玩家、公开/暗置攻击和事件揭示。
- 战斗结算显示完整威力 breakdown，而非只给最终数字。
- 胜者、败者、并列、差值、战果、军事结果、令咒变化和胜败后触发依次进入结构化结果。
- 幸运等“忽略败北效果”只影响对应结算层，不改写是否参战和原始威力。
- 清理阶段把不残留的基础攻击移入弃牌堆；带残留效果的攻击继续留在攻击区。
- 残留攻击即使纸面威力为 0，仍作为已激活的有属性攻击参与属性修正。
- 所有清理和回合末能力完成后进入下一回合；第 11 回合执行最终胜负结算。

## 5. 战场棋盘设计

### 5.1 地点节点

每个地点是一个完整的横向战场带，不做悬浮卡片套卡片。节点包括：

- 左侧：地点编号、名称、公开状态、容量、竞争战果、移动成本。
- 中部：地点背景和玩家占位区。
- 中右：地利位或工房位方格。
- 最右：事件牌横向队列。
- 底部：没有占据地利/工房的普通参战者头像行。

### 5.2 地利和工房槽位

槽位必须可视化为独立方格：

- 每格固定显示 `+3`、`+1` 或对应工房魔力。
- 占据者显示从者圆形头像、席位色和席位号。
- 悬停显示主从名、进入方式和占据时间。
- 后续移动进入战场者只能进入普通占位行，不得挤掉原地利玩家。
- 地利归属使用后端稳定 assignment，不按当前 occupants 数组顺序推断。

### 5.3 事件牌

- 所有事件位于战场右侧，按从左到右横向排列。
- 第一张和额外事件使用相同方向，不旋转卡片本体。
- 明置事件展示真实卡图、名称和战果；暗置事件展示统一事件背面和“暗置”。
- 暗置事件必须作为匿名实例投影，不能因为前端拿不到卡图而消失。
- 点击明置事件打开卡牌检视；暗置事件在无权限时不能打开正面信息。
- 事件多于可见宽度时横向滚动或叠放 20%，不覆盖右侧决策栏。

## 6. 本人作战中心

### 6.1 两段高度

观察模式只展示：主从头像、资源、手牌/牌库/弃牌/技能/攻击区数量、当前是否有待处理窗口。

以下情况自动进入操作模式：

- 当前席位获得优先权。
- 打开支付、目标、模式、响应或房主裁定窗口。
- 玩家点击手牌、技能、令咒、攻击区或弃牌堆。
- 存在待确认攻击。

操作模式高度为 `clamp(520px, 56vh, 780px)`；关闭交互并完成本次行动后自动收回。玩家可手动固定或收起。

### 6.2 展开布局

```text
┌──────────────┬────────────────────────────────┬───────────────────┐
│ 身份与资源   │ 当前操作画布                   │ 技能与特殊区域    │
│ 主从小头像   │ 待确认攻击 / 攻击区            │ 御主技能          │
│ 魔力/VP/令咒 │ 支付、目标和战斗预览            │ 从者技能/升华技    │
│ 牌库摘要入口 │ Ghost Slot 仅操作时出现         │ 令咒/独立牌堆      │
├──────────────┴────────────────────────────────┴───────────────────┤
│ 手牌扇形托盘                         牌库 / 弃牌 / 移除区入口    │
└──────────────────────────────────────────────────────────────────┘
```

静态的“从者牌库构成第一张图”不常驻占据空间。点击从者头像或牌库摘要后，在检视抽屉中显示真实构成、当前剩余数量与已知牌。

### 6.3 手牌

- 使用水平重叠而非缩小平铺，卡片保持可读比例。
- 悬停/键盘聚焦的单张牌上浮并放大，保持其余卡片位置稳定。
- 费、威、时和属性使用高对比信息条；不叠加一套与原图冲突的错误文本。
- 有真实卡图时以真实图为主；结构化字段用于可访问文本、筛选和规则窗口。
- 手牌只能由本人和具备裁定权限的房主看到。

### 6.4 技能与令咒

御主本体技能、升华技、从者技能和令咒是四个独立区域。升华技不能混入御主原始技能。

每张技能卡显示当前状态：可发动、当前阶段不可发动、已关闭、被禁用、等待目标。只有后端提供 `activate_ability` 时才显示发动操作。被动或“被动/阶段”技能若规则为可选，也显示“发动/不发动”窗口；不把它们错误命名为常规主动技能。

令咒区显示剩余实体/计数和三个可重复选择的基础效果。只要令咒仍有剩余、时机合法，同一效果可以再次使用。特殊御主允许在准备、前哨或战斗阶段使用令咒时，由后端为该阶段投影相应 action。

### 6.5 攻击区

攻击分为两个区域：

- 待确认攻击：本次计划，尚未提交，可取消或确认。
- 攻击区：已经打出、该回合对其他玩家公开并参与规则计算的牌。

援护射击不是挂在卡牌说明上，而是通过目标选择后加入目标玩家的攻击区。战斗阶段合法追加的牌也进入同一攻击区。残留牌跨回合保持激活，直到后端生命周期规则关闭或移走。

### 6.6 私有牌堆

- 牌库：显示剩余张数；默认不展示未知顺序。
- 弃牌堆：本人可打开并查看全部牌，其他玩家只看到数量。
- 移除区：按卡牌公开性投影。
- 独立牌堆/替换牌：起源弹、援护射击等显示独立入口和数量。
- 手牌、弃牌、牌库底查看等权限由 `visibleZones` 决定。

## 7. 卡牌呈现与资产规则

### 7.1 数据优先级

```text
卡牌身份/规则字段：authoring JSON
牌库构成：servant JSON 的结构化 deck 数据
卡面图像：asset manifest 的明确 cardId -> image 映射
显示文本：结构化名称 + 规则文本；不得用 OCR 猜牌库
```

主从 manifest 图号必须通过卡牌 ID 校验，不能按目录顺序或“第一张/第二张”推断。七名从者牌库各自建立精确构成测试。

### 7.2 基础攻击牌

基础牌必须区分属性和数值：力量、敏捷、魔术以及特殊牌。特殊牌首版固定为：

| 卡牌 | 魔力 | 威力 | 核心效果 |
|---|---:|---:|---|
| 远隔操作 | 1 | 2 | 行动阶段地利效果翻倍；获胜后增加战果 |
| 急行 | 1 | 3 | 行动阶段无视交战，沿箭头移动一步 |
| 幸运 | 0 | 4 | 战斗阶段无视本回合直接败北；行动阶段已直接败北则不能打出 |

优先使用已导入的真实卡图。没有真实图的内容使用产品级占位卡面，但占位图必须明确来源和 cardId，不能展示与名称、技能不符的图片。

### 7.3 卡牌检视

点击卡牌打开固定层级的检视器：左侧完整卡图，右侧为名称、类型、所属、公开性、费用、威力、时机和结构化规则文本。检视器不得遮挡关闭按钮，不得与右侧决策栏互相覆盖；可通过 Esc 关闭并恢复原焦点。

## 8. 通用交互窗口

所有窗口使用统一容器，字段完全由后端契约生成。

### 8.1 支付窗口

- 固定费用和额外费用逐项显示。
- X 值使用步进器/滑杆和数值输入，范围来自后端 `min/max`。
- 展示支付前后资源预览；资源不足时确认按钮禁用。
- 取消不会推进状态；服务端拒绝时保留选择并展示 reason code。

### 8.2 目标窗口

支持卡牌、玩家、地点和选项目标，显示 `min/max`。棋盘目标在地图上同步描边；区域内卡牌目标在对应抽屉中高亮。前端只能从 `candidates` 选择，不能自己补候选。

### 8.3 响应与能力窗口

- 显示来源卡、控制者、触发时机和正在等待的玩家。
- 可选效果提供“发动/不发动”。
- 多能力同时触发时先选择唯一触发，再处理其支付和目标。
- 放弃响应记录为正式 command，不能只关闭弹窗。
- 响应顺序由后端确定；非相关玩家只看到等待状态。

### 8.4 模式、替换与追加

模式选择、盖放/公开、追加打出、替换方向、查看牌库底和牌组替换均使用结构化选项。选择结果写入 command 的 mode/variables/selectedIds，不使用自由文本 directive 代替可执行操作。

### 8.5 Directive 与房主裁定

Directive 分三类：

- `display`：后端已结算，仅供说明，可标记已读。
- `player_decision`：必须转换为目标、模式或确认窗口，由当前玩家处理。
- `host_adjudication`：确实无法自动结算时暂停，房主选择结构化结果并留下理由。

会影响合法性的 directive 未处理前，MatchSession 必须暂停。房主可点击“暂停并报告问题”，生成包含 revision、卡牌、能力、当前窗口和最近日志的本地诊断包。

## 9. 右侧决策栏

右栏按优先级只突出一个主任务：

1. 当前必须处理的 interaction window。
2. 当前阶段 legal actions。
3. 可选能力。
4. 未处理 directive。
5. 战斗 breakdown、日志、回放等辅助内容。

原“PUBLIC INTEL”悬浮栏取消。公开技能与公开牌通过玩家详情抽屉、攻击区和战场事件直接查看，避免覆盖棋盘和卡牌检视。

主确认按钮固定在决策栏底部，文案随上下文变化，例如“确认支付”“确认目标”“确认攻击”“完成准备”“结束行动”。按钮只在服务端存在对应 command 时可用。

## 10. 玩家详情与信息权限

点击席位或战场头像打开玩家详情抽屉。

| 信息 | 本人 | 其他玩家 | 房主裁定 |
|---|---|---|---|
| 御主公开卡与公开技能 | 可见 | 可见 | 可见 |
| 未解放从者身份/隐藏技能 | 可见 | 隐藏 | 按裁定权限 |
| 手牌内容 | 可见 | 仅数量 | 按裁定权限 |
| 牌库顺序 | 规则允许时 | 隐藏 | 按裁定权限 |
| 弃牌内容 | 可见 | 仅数量 | 按裁定权限 |
| 攻击区与公开残留 | 可见 | 可见 | 可见 |
| 暗置事件正面 | 规则允许时 | 隐藏 | 按裁定权限 |
| 当前相关响应窗口 | 可见 | 等待提示 | 可见 |

服务端必须产生独立玩家投影。前端隐藏 DOM 或 CSS 不算权限实现。

## 11. 战斗展示

战斗开始后，棋盘切入对应战场焦点，展示：

- 参战者和地利占位。
- 每名玩家攻击区中的激活牌与残留牌。
- 暗置牌揭示动画及来源。
- 逐层威力 breakdown：纸面值、属性修正、技能修正、事件/局势修正、地利、倍增、最终值。
- 直接败北、败北免疫、未参与结算等独立状态，不混入威力数字。
- 胜者、败者、并列、差值、公共战果和个人额外战果。
- 战后触发队列以及令咒、军事结果、卡牌区域变化。

每一行 breakdown 需带 sourceId/sourceName，点击可检视来源卡或规则。战斗完成后保留摘要，并可从日志重新打开完整详情。

## 12. 房间、同步与恢复

### 12.1 房间能力

- 创建/加入房间、七席选座、房主移交、主从分配和准备确认。
- 服务端维护 room revision、session revision、连接身份和观战权限。
- 本地七席模式使用同一 room/session 模型，只是允许测试者切换全部席位。

### 12.2 实时同步

所有客户端收到同一权威 revision 的差异或快照，再按身份生成视图。command 携带 `expectedRevision` 和幂等 ID：

- 旧 revision：拒绝并刷新。
- 重复 command：返回原结果，不重复扣费或移动卡牌。
- 断线重连：恢复当前优先玩家、未完成窗口、计时/等待状态和可见区域。
- 新连接不能收到历史上本不应看见的隐藏信息。

### 12.3 保存与回放

保存包包含 seed、内容版本、完整 session state、revision、未决窗口、结构化日志和最近 checkpoint。回放允许跳到任意 checkpoint，再按日志命令重建至目标节点；查看回放默认只读，分支恢复必须显式创建新 session 分支。

## 14. 服务端投影契约

客户端视图至少包含：

```ts
interface MatchClientView {
  revision: number;
  viewer: { playerId?: string; role: 'player' | 'host' | 'spectator' };
  match: { round: number; phase: PhaseId; step: string; priorityPlayerId?: string };
  players: PublicPlayerView[];
  locations: LocationView[];
  cards: VisibleCardView[];
  visibleZones: ZoneView[];
  legalActions: LegalActionView[];
  interactionWindows: InteractionWindowView[];
  directives: DirectiveView[];
  battle?: BattleResolutionView;
  logs: PublicLogView[];
  replay: ReplayCheckpointView[];
}
```

关键约束：

- `phase` 使用稳定枚举，不靠中文文案解析。
- 地利占据者与普通 occupants 分开投影。
- 暗置事件投影匿名 instance 和背面资源，不投影真实 cardId。
- 每个 legal action 带 command 模板、来源、reason label 和必要候选。
- 每个窗口带控制者、可见者、min/max、候选、取消/放弃能力和阻塞级别。
- 区域明确 `visibility`、`count`、`cardIds` 是否可见以及是否可打开。

## 15. 视觉与可用性规范

- 风格为克制的暗色作战台，金色用于优先权和确认，红色只用于危险/拒绝，蓝绿用于信息与资源。
- 不用大面积单一深蓝或紫色；地点实景和真实卡图承担主要视觉信息。
- 卡片、槽位、按钮使用稳定尺寸，hover 不改变父容器布局。
- 费、威、时不遮盖原卡关键区域；字体不随 viewport 连续缩放。
- 图标按钮使用项目现有图标库并带 tooltip；明确命令可用图标加文字。
- 所有浮层有唯一 z-index 层级：棋盘 < 操作台 < 右栏 < 抽屉 < 卡牌检视 < 模态窗口 < 致命错误。
- 键盘支持 Tab、Enter、Space、Esc；目标选择和错误信息具有可访问标签。
- 动画遵守 `prefers-reduced-motion`，不能延迟规则确认。

## 16. 错误与暂停策略

错误分为四级：

- 输入错误：留在当前窗口，指出范围或缺失目标。
- 服务端拒绝：展示 reason code，刷新 legal actions，不静默跳阶段。
- 同步冲突：提示状态已更新并拉取新 revision，保留可安全恢复的 UI 上下文。
- 规则无法处理：冻结自动推进，生成 host adjudication 或“暂停并报告问题”。

防死循环记录连续状态指纹；相同状态和相同拒绝超过阈值时停止 AI/自动推进，并明确显示最后 command 与来源能力。

## 17. 验收场景

### 17.1 组件验收

- 支付：固定额外支付、X 支付、资源不足、取消和服务端拒绝。
- 目标：卡牌、玩家、地点、多选 min/max 和零目标放弃。
- 响应：发动、放弃、唯一触发、多席等待。
- 操作台：观察/操作两段高度、手牌扇形、抽屉和焦点恢复。
- 棋盘：多事件横排、暗置背面、地利头像、普通占位不挤地利。

### 17.2 规则场景验收

- 事件放置后进入准备并抽牌；准备阶段不出现普通部署。
- 普通前哨部署不能进侦察，工房部署即时获得正确魔力。
- 后移动者不占据已分配地利。
- 令咒效果可重复选择，直到令咒耗尽。
- 无额外许可玩家不能提交超量攻击。
- 远隔操作、急行、幸运的费用、威力、卡图和效果链一致。
- 起源弹替换、援护射击加入目标攻击区、残留攻击跨回合均可通过 UI 完成。

### 17.3 运行验收

按顺序执行：

1. 一回合七席全人工点击流。
2. 三回合事件牌 smoke，覆盖暗置、揭示、额外事件和回收。
3. 交互窗口组件测试。
4. 11 回合确定性半自动完整运行。
5. 多 seed 和复杂技能回归。
6. Chromium、Firefox、WebKit 的关键点击流与断线重连。

未完成前不运行全仓测试。每个切片先跑直接相关的 rules/client 定向测试。

## 18. 实施优先级

### P0：规则与交互可信

- 完整普通移动、令咒移动、卡牌移动命令。
- 地利、事件暗置、攻击数量和区域生命周期后端权威化。

### P1：棋盘和操作台重构

- 拆分 `MatchTable`。
- 重做地点槽位、横向事件和玩家详情。
- 实现 52%-60vh 作战中心、手牌扇形和私有区域抽屉。
- 完整攻击区、令咒区、升华技区和战斗 breakdown。

- 七对主从及相关卡牌真实资产映射校验。

- 11 回合产品验收和性能修整。

## 19. 完成定义

本产品只有在以下条件同时满足时，才能称为“完整棋盘对局已跑通”：

- 11 回合状态机、事件调度、战斗和最终胜负可通过真实客户端完成。
- 七席人工、本地加 AI、七客户端联网均走同一 MatchSession dispatch。
- 所有必需选择都有可操作窗口，不依赖开发者修改状态或阅读 directive JSON。
- 公私信息、暗置事件和未解放身份通过服务端投影验证。
- 关键卡牌区域、移动、攻击、残留和令咒规则有正反例测试。
- 保存/重连能恢复当前窗口，回放可定位到具体卡牌、能力和 state delta。
- Chromium、Firefox、WebKit 的关键点击流通过。

在此之前，应准确报告尚未验证的切片，不能用“页面可打开”替代“完整产品可运行”。
