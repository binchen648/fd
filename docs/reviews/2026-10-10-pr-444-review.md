## Blocking Finding

**P2: Ordinary close protection incorrectly prevents the target's own required
close effect.** `packages/rules/src/ability/interpreter.ts:1218` unconditionally
rejects `close_source_card` when `isCardCloseForbidden` matches. The typed route
at `packages/rules/src/ability/resolution-dataflow.ts:1488` has the same behavior.
The query at `packages/rules/src/ability/card-close-forbid.ts:36` receives only
state and target ID, so neither route distinguishes another player's close from
the source card's own required close.

Final Rules 11.4 (`docs/rules/FD-Game-Rules-Final.md:444`) states that ordinary
protection does not prevent round-end rule closure or a card's own required
closure. No explicit self-close exception is represented by the admitted
modifier or provided by the synthetic ward. An independently authored automatic
phase action containing only `close_source_card` is listed as legal, but the
authenticated `dispatchAbilityCommand` returns `resolution_failed` with the
live-forbid message. Typed resolution rejects the same own-close as well.
This proves the rule-boundary issue at an actual dispatch, not just a direct
helper invocation. No product consumer migration is present or claimed.

The guard is new relative to this exact base. The same selector/query is inherited
from historically accepted PR394 (only final newline differs), and the A dispatch
explicitly asks for unconditional protection on both close routes. Consequently
this is also a **dispatch/source-contract conformance issue**, not evidence that
the implementer replayed that historical contract inaccurately. Historical
acceptance cannot override the higher-priority Final Rules. Planner/runtime
owners must resolve causation/exception scope before a rule-conformance PASS;
this reviewer does not silently revise the accepted contract or implement a fix.
