## Findings

### P2: Invalid marker containers are silently normalized and accepted

New helper next-round-situation-benefit-suppression.ts:157-164 validates entries
but not the map container. For [], true, false, 7 and an empty string,
Object.entries produces no entries, then object spread silently replaces the
invalid value with a normal map. Independent dispatch probes observe ok=true
and the corrupted field rewritten to {p2:2}, with revision/usage also committed.

The exact dispatch requires malformed state to fail/no-op transactionally without
partial marker mutation. Existing tests exercise NaN marker values and unknown
player keys, but not these invalid container values. A positive valid map works,
and negative integer/unknown-key controls reject preserving the whole state.
Validate the container before enumerating/spreading it; distinguish an absent
optional field from supplied invalid JSON types. This is a trusted-state robustness
finding, not a demonstrated client or snapshot-forgery exploit.

### P2: Scheduling the following round erases an already-current suppression

The same helper at line164 stores one scalar round per player. In an exact accepted
generic envelope fixture with no per-game limit, activation in round1 marks p2
for round2. After authoritative advanceAbilityPhase to battle round2, situation
mana is correctly zero. A second accepted activation writes p2=3; a subsequent
round2 situation grant now yields 2 instead of zero because the predicate at
line170 only matches the new scalar. Scheduling future suppression has cancelled
the existing current-round effect early.

The previous marker should remain effective throughout its marked round. A new
next-round effect must not remove that prior obligation. The dispatch's prescribed
single-round map does not represent simultaneous current/future obligations, so
the implementation and contract may need a bounded representation reconciliation.
Do not broaden to a generic flag engine or change semantics silently.

This reproduction proves the accepted generic API/envelope behavior only. The
frozen Ciel S3 consumer is described as once-per-game, is not authored in this
candidate, and no claim is made that the same Ciel card may legally repeat in a
production match. Real multi-source/consumer integration remains unverified.
Consumer restrictions do not presently constrain the accepted helper envelope
with limit={}, which permits the demonstrated consecutive activations.

Both fields/helper logic are new relative to this exact base. Neither finding
relabels the inherited FB2-50/51 defects as new changes in this PR.
