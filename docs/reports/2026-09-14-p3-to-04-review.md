## Blocking Findings

### [P1] Fixed-duration policy cannot represent the actual expiration scheduling boundary

The candidate correctly refuses to default whether the installation round counts. Its normalized type has:

```ts
type RoundBoundaryConvention =
  | 'start_round_inclusive'
  | 'next_round_boundary';
```

and `round_count` carries `rounds` plus `boundaryConvention`.

That answers **which round ordinal** is due, but not **at what authoritative scheduler boundary** the expiry transition occurs. The contract does not encode whether expiry happens at a reviewed round-end cleanup point, a transition into the new round, before/after round-start triggers, or another named lifecycle boundary.

The prose says the current Artoria Caster row remains blocked until exact timing is confirmed, which is safe, but the normalized contract has nowhere to store that confirmation once it exists. A later runtime would still have to hard-code scheduler placement outside the lifecycle policy.

Required repair:

- add an explicit normalized expiry/scheduler boundary reference for fixed duration;
- make it server-owned and derived from a reviewed round/lifecycle boundary contract, not card ID or source-file order;
- fail admission when a movement/effect-producing fixed duration lacks the required boundary;
- include stable ordering/causation/idempotency at that boundary;
- keep the current `rounds=2` consumer blocked until its exact boundary is independently confirmed.

### [P1] `while_card_active` has no normalized source-validity / active-area policy

The prose requires source existence, active state, controller, ability validity, and an "accepted active area". But the normative `while_card_active` policy contains only:

```ts
{
  kind: 'while_card_active';
  starts: 'immediate';
  cleanup: 'when_card_leaves_active_area' | 'remain_active';
}
```

There is no normalized field/reference defining which authoritative source states/zones constitute the active area or how a closed/face-down/moved source invalidates this lifecycle. A later implementation could therefore satisfy the prose only by hard-coding `field`, `attack_area`, or card-specific zone rules in Lifecycle.

This is especially material to P3-B08: CLOSE must compose with Lifecycle without Lifecycle owning or guessing Card Zone semantics.

Required repair:

- add a normalized `sourceValidity` / `activeAreaPolicyRef` concept to source-bound duration policy;
- that policy must be supplied/resolved by an accepted Card Zone/source-state owner before runtime admission;
- Lifecycle may consume the resulting active/inactive/source-left transition but may not define card movement itself;
- missing/unknown source-validity policy must fail closed;
- ability map/checklist/negative matrix must make this dependency explicit.
