## [P1] Event and competition base-pool provenance can be misimplemented as independently rounded shares

Canonical rule 12.5 defines one base pool:

`base pool = event VP total + competition VP`

Then each tied winner receives exactly:

`ceil(base pool / winner count)`.

Event and competition VP are gained simultaneously. They are not separately rounded reward pools.

The R4 schema exposes separate `event_pool_share` and `competition_pool_share` adjustment sources but does not state a mathematical reconciliation invariant. Counterexample:

- winners = 2
- event pool = 1
- competition pool = 1
- canonical combined result per winner = `ceil(2 / 2) = 1`
- independently rounded component shares = `ceil(1/2) + ceil(1/2) = 2` (wrong)

Current runtime happens to avoid this by computing `baseVpPerWinner` from the combined pool and assigning competition as the remainder after the event attribution, but TO-14 must not rely on current implementation order as the normative contract.

Required repair:

1. Represent the event+competition reward as one typed **combined base-pool share** adjustment or define an equally strict reconciliation rule that mathematically guarantees one rounding over the total pool only.
2. Preserve event and competition provenance as components of that combined source; do not lose auditability.
3. For each winner, the sum of base-pool adjustments must equal exactly `ceil((eventVpPool + competitionVpPool) / winnerCount)`.
4. Event and competition components are simultaneous; component attribution must never change the awarded total.
5. A separately reviewed location reward may remain outside the combined base pool if its rule defines separate settlement. Recon remains phase-level and separate.
6. Add negative/checklist coverage for the 1+1 / 2-winner counterexample or equivalent rounding divergence.

No denominator/runtime change is required.
