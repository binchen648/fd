## Blocking finding

### [P1] Generic stage order settles post-result win/loss triggers before base battle scoring

The current stage model says:

1. determine Battle Result;
2. produce result/win/loss/first-loss events;
3. Trigger Gateway settles result-dependent windows;
4. only then consume the base scoring plan.

Canonical battle rules require the opposite ordering for battle rewards and personal win/loss rewards:

- Section 12.5 computes and awards the shared/base battlefield reward first.
- "获胜后额外获得" personal VP from command spells, masters, servants, or other effects is resolved **after the base reward split is complete** and is not part of the shared pool.
- The example explicitly says the base pool is distributed first, then each winner's personal rewards are processed.
- Round cleanup ordering also places "战斗后 / 若获胜或战败" effects in the post-battle processing stage, after battle resolution.

Several direct TO-14 consumers make this material, including:

- Artoria Alter `noble-bloom` / extra VP;
- Artoria Caster non-sole-winner +2 VP;
- Tomoe defeat -5 VP;
- other win/loss transforms/reveals.

Required repair:

1. Battle Result may be committed first and its domain events may receive stable identities / be queued, but their effect continuations must not generically settle before base battle scoring.
2. Commit the immutable base scoring plan and typed base VP/military/resource settlement exactly once before opening post-result personal win/loss reward/effect settlement.
3. Treat personal trigger-earned VP as separate Resource results linked to the same Battle Result; never fold them into the base pool.
4. Define an explicit **post-base-scoring trigger barrier**. Result/win/loss/first-loss/gains-victory consumers cross that barrier before settlement unless a reviewed card/rule explicitly defines an earlier timing.
5. Keep `after_battle_ended` terminal after those post-battle trigger windows, then hand off to cleanup/lifecycle.
6. If a future effect truly modifies the base scoring plan before commit, it needs a distinct reviewed pre-scoring contract/orderingRef; TO-14 must not silently classify ordinary post-result triggers that way.
7. Update checklist/result notes with the base-score-before-personal-reward invariant.
