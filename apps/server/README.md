# Match server recovery

`npm run dev --workspace @fd/server` persists confirmed room creation, joins, seats and game operations before sending success/projections. The entry point uses `.fd-server/rooms.json` relative to the server's working directory. Set `FD_STATE_FILE` to an absolute path on a persistent private volume for deployment. Keep the file **and** its sibling `.key` together; neither belongs in public assets, source control or client downloads. The file is authenticated/encrypted; its key is private server material. Restrict the directory ACL on Windows. POSIX files use mode 0600 and new directories use 0700.

On restart the server validates the file and existing session seals, restores original client credentials and marks old connections offline. Clients retry with bounded backoff and wait for a fresh projection before sending, without replaying buffered game commands. The existing reconnect token remains required. Duplicate/old revision commands continue to be rejected by the authoritative hub.

Only one process may write a state file. A sibling PID lock rejects a live second writer; after a killed process the next instance reclaims a dead PID lock under an exclusive `.lock.recover` guard. A crash during lock recovery can leave that guard: startup then fails closed. After confirming no process owns this store, an operator may remove the stale guard; never remove a live writer's lock. Invalid locks, absent keys for an existing state, corrupt files or unsupported versions stop startup without replacing evidence. A save failure stops further mutations and makes `/health` return 503; restart after repairing storage recovers the last durable state. A command interrupted before its success projection may be unconfirmed: refresh state and decide again rather than replaying it automatically. Client connection flags are ephemeral and are not flushed on disconnect.

This is single-process local-file persistence, not distributed replication or a guarantee against disk/volume loss. Preserve and back up both encrypted state and key. POSIX saves flush the file, atomically rename, then flush the directory; Windows flushes the file before rename and depends on the filesystem for rename durability across power loss. `createMatchServer()` remains an explicit in-memory test helper unless passed `stateFile`.

Validation: `npm run typecheck`, `npm test --workspace @fd/server`, `npm run test:client`, and `npx playwright test e2e/fd-server-recovery.spec.ts` from repository root. Recovery acceptance starts the production entry in a real child process, kills it after confirmed UI operations, restarts on the same port and continues all seven browser seats without reloading. Full roster and all capability-specific recovery contracts are separate acceptance scopes.
